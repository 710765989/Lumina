# 大批量操作并发情况

2026-10-20，M2 .4.8.8。后台进程、异步并发和多个JavaScript工作线程是不同概念。当前未引入worker_threads工作池。

| 模块 | 当前代码行为 | 后续可优化方向（未实现） |
|---|---|---|
| 核心服务 | Electron启动独立stdio核心进程，避免直接占用界面进程 | CPU密集特征可引入受限工作池 |
| 目录扫描 | 同目录合并；元数据全局4份并发、视频探测最多2份，向前准备4项、按原顺序写SQLite；未变复用，500ms通知/5秒统计 | 真实HDD/SSD及多目录规模评估，小批数据库事务 |
| 缩略图 | 首次校验与生成共享3槽并去重；主进程JPEG字节LRU上限32MB、文件读取4槽，磁盘指纹变更即失效；sharp原生线程，视频FFmpeg子进程 | 测量冷缓存读取/校验瓶颈，统一预算避免多个任务各自占满 |
| 批量标签 | 一条持久批次；逐媒体事务并写逐项结果，数据库写串行 | 小批事务同时写变更和结果，定期让出事件循环；不能一口气大事务阻塞取消/查询 |
| 删除/还原/回收站 | 逐项文件操作与检查；后台可暂停/取消 | 对无关联文件评估少量并发，保留代表项核验、重名保护、事务/取消语义 |
| 完全重复/相似 | 逐项哈希/特征；sharp原生解码；指纹缓存复用 | 独立文件受限并发，CPU特征再评估工作线程 |
| 缓存移动（本轮已改） | 最多4文件复制/校验并发，2文件旧副本清理；每32项或200ms合并进度写入 | 实测HDD/SSD与真实图库后调整预算，不按文件数无限并发 |

文件系统异步I/O会使用Node底层设施；createHash.update仍在核心事件回调中执行，并不是独立的JavaScript哈希线程。SQLite写入应继续统一排队，不靠增加写线程提速。不能把界面可操作等同于每个批次已充分并行。

任何后续优化都需保留逐文件历史、原件保护、暂停/取消、重试去重及原子切换，并测量真实规模。本轮实现扫描元数据受限并发与缩略图读取复用；标签、删除、重复/相似等仍是表中既有行为，后续项未冒称完成。

缓存统计：schema9持久逐文件清单，生成/删除/迁移增量维护；首次建立或手动校准才全量遍历缓存目录，日常与扫描后归类只读清单。校准通过版本保护同期增删。
